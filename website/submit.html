port / publish

From a GGUF on Hugging Face to a row on the board.

Three commands. weaver ports the model with a local agent, validates it against llama.cpp ROCm, and publishes the package with a card written from the benchmark report. There's no form to fill in.

01install

Install weaver

One package from PyPI that brings hrx-loom, the Pi agent, the pinned loom-skills and the Loom library with it. You need Python and pip, but no Node.js, ROCm SDK or git.

shell
$ pip install loom-weaver
$ weaver init
weaver init runs once. It fetches and serves the local agent model, smoke-tests the agent against it, and pre-fetches the llama.cpp ROCm reference. weaver doctor tells you what the machine is missing.
02port

Port and validate

The agent ports the checkpoint, qualifies it against llama.cpp ROCm (gates, baselines, speculative-decoding choice) and finalizes it (full gates, audit, report). It never stops to ask, except to accept a gated model's license.

shell
$ weaver port <org>/<model>
Want it faster? Run weaver optimize <org>/<model> [TARGET] [BUDGET] instead, with a target of roofline (the default), beat-llamacpp or something like decode+30%, and a budget like 90m or 3h.
03upload

Publish to Hugging Face

weaver stages the programs, a model.json that points at the upstream GGUF, and model.json.lock. The agent writes the model card from the benchmark report. You see a preview first, and nothing is published until you confirm.

shell
$ weaver upload <org>/<model> <hf-org>
Every number on the card has to come from the report. Without a report, the card has no performance section.
04listed

Show up on loom/dev

The index reads public Hugging Face models tagged loom and loom-serve. On the next refresh your model gets a leaderboard row, a detail page and a quick start. Anyone can then serve it:

shell
$ weaver serve huggingface://<hf-org>/<repo>

requirements
  • Linux x86-64 with glibc 2.39 or newer (Ubuntu 24.04+). Windows will follow.
  • An AMD GPU with /dev/kfd access. Developed on Strix Halo (gfx1151, 128 GB).
  • About 64 GB of RAM. The agent model holds about 42 GiB while it works.
  • A Hugging Face account with a write token, to publish.

faq

Questions people ask before their first port.

Does anything go to a cloud model?

No. weaver runs the loom-skills with a local agent: Pi driving Qwen3.8-27B on loom-serve, on your machine.

Which checkpoint does weaver pick?

A checkpoint is huggingface://org/repo[:file.gguf], org/repo or a huggingface.co URL. Without a file, weaver uses plain Q4_K_M from your Hugging Face cache. Speculative decoding is on whenever the GGUF supports it; --no-spec turns it off.

Which architectures can it port?

The starter kit covers dense transformers and Qwen3.5-style gated delta-net hybrids, with vision projectors and speculative-decoding drafters where the model has them. Anything else goes through the hand-port playbook in loom-port-llm, which takes longer.

My port is slower than llama.cpp on some workloads. Should I still publish?

Yes. The index shows every workload, including the ones where llama.cpp is faster. A working, verified port is the useful part, and a slow workload is a clear target for weaver optimize.

What does "no evidence" mean on a gate?

The gate applies to the model, but no recorded run covers it yet. A full finalize.sh run fills it in.

How is the leaderboard ordered?

By the geometric mean of Loom's throughput over llama.cpp's across every workload the model was measured on: decode at short, 2k and 32k context, prefill on 1k to 32k documents, and 4-stream aggregate decode. Missing workloads are skipped. You can re-sort by any column.

How do I remove my model?

Remove the loom tag from the card, or make the repository private. It drops off on the next refresh.
